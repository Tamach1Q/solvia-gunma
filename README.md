# SOLVIA 点検・保守管理デモ

太陽光発電所の定期点検を「点検予定 → 点検準備 → 現場入力（スマホ）→ 報告書 → 修繕案件 → 発電所カルテ → 次回点検」まで1周操作できるデモです。測定値は入力した瞬間に判定され、報告書は入力データから自動で作られます。

## 起動

```bash
npm install
npm run dev                       # 管理画面のみ（http://127.0.0.1:5173）。現場入力は「同じ端末のモード」になる
npx netlify dev --offline         # 現場共有（Netlify Functions / Blobs）込み（http://localhost:8888）
```

- **共有URLモード**：管理画面の「現場に依頼」で発行したURLをスマホで開くと、現場画面だけが開きます。入力はその場で管理画面に反映されます（5秒ごと）。URLの末尾に `&fill=1` を付けたとき（依頼の画面の「一括入力つきURLをコピー」）だけ「残りを一括入力」が出ます。スマホから開くには、Netlifyにデプロイしたサイトか、スマホから届くアドレスで `netlify dev` を動かしてください（`localhost` はスマホから開けません）。
- **同じ端末のモード**：依頼の画面の「この画面で現場入力を開く」（Functionsに繋がらないときは「この端末で現場入力を開く」）を選ぶと、管理画面の右にスマホ枠で現場画面が開きます。データはこの端末のブラウザに保存され、「残りを一括入力」がいつでも使えます。オンライン会議の画面共有はこのモードで行います。
- 報告書の発行者名は `src/config/brand.ts` で変えられます。

## 確認

```bash
npm test                          # 単体テスト（判定・確認ポイント・提案文・報告書・修繕・保存）
npm run build                     # 型チェック＋ビルド
npm run test:flow                 # デモ台本どおりに1周するE2E（同じ端末のモード）。先に npm run build
npm run test:flow -- http://localhost:8888   # netlify dev に対して実行すると、共有URLモード（スマホ幅）で1周する
```

初回は `npx playwright install chromium` が必要です。スクリーンショットと報告書のPDFは `artifacts/` に出力されます。

## デモ手順（台本）

操作は約15分です。始める前に、点検予定の右上「初期状態に戻す」でデータを初期化しておきます（日付は当日を基準に作り直されます）。

1. **点検予定**（1分）：今月の点検が、近くの発電所ごとにエリアでまとまっていることを見せる。統合監視では、監視システムが違う発電所の状態と修繕中の案件をまとめて見られる。
2. **点検準備**（2分）：「広川町 第2太陽光発電所」を開く。「今回の確認ポイント」に、PCS-2 回路2の絶縁抵抗が 25→18→12MΩ と3回連続で下がっていること（初回比−52%）が理由付きで出ている。前回の雑草の指摘も重点確認として出る。
3. **現場に依頼**（2分）：オンライン会議で画面共有しながら進める前提。「現場に依頼」で現場用URLを発行し、依頼の画面で「この画面で現場入力を開く」を押す。管理画面の右にスマホ枠の現場画面が開き、入力すると左の点検準備がその場で変わる様子を見せられる。先方に自分のスマホでも試してもらう場合は、「一括入力つきURLをコピー」でURL（末尾に `&fill=1`）をチャットで送る（任意。先方の入力は、画面共有している点検には取り込まれない）。
4. **現場入力**（4分）：天候を選んで開始し、「測定」で数値を2〜3個、先方に読み上げてもらって入力する。打った瞬間に適合／不適合と判定理由が出る（例：絶縁抵抗に 0.35 → 不適合、85 → 適合）。「確認」の「残りを一括入力」で残りを埋める（手で打った値は残る）。一括入力では PCS-2 回路2 が 0.3MΩ（不適合）、アレイB 1段目5列目のパネル割れ（目視×）になる。入力漏れチェック → 提出。
5. **報告書**（3分）：点検準備の「写真を確認して報告書へ」→「報告書の配置編集へ」。総合判定、目視・測定の結果、異常箇所（アレイ図）、交換のご提案が自動でできている。写真は右の一覧から本文へドラッグで配置できる。「印刷／PDF保存」でA4のPDFにする。
6. **報告書チェック**：報告書の「報告書チェックに提出」で同じ案件をチェック待ちにする。「AIチェックを実行」で内容を確認し、担当者名と全体確認を入力して承認。点検予定にも「承認済み」と承認者が表示される。差し戻しを見せる場合は、提出前に「文章・宛名を編集」でオーナー名を変えておき、チェックで指摘 → 理由を添えて差し戻し →「元の報告書を修正」→ 正しい名前に戻して再提出 → 再チェック・承認まで進める。
7. **1周を閉じる**（3分）：承認した報告書を開き、「点検を完了する」で修繕案件が2件でき、1年後の点検予定が入る。修繕案件でパネル割れを「交換」→ 作業予定 → 作業内容・写真・再測定（85MΩ）で完了すると「修正済み」になる。発電所カルテで今回の0.3MΩを含む推移と次回点検を見せる。点検予定の「来月以降の予定」に1年後の予定がある。
8. **フィードバック**：「御社の報告書フォーマットに合わせるなら何を変えるか」を聞く。

## 報告書チェック

サイドバーの「報告書チェック」には、チェック待ちを提出日時が古い順に、下段にはすべての提出記録を表示します。発電所名・オーナー名・担当者名で検索し、チェック待ち／差し戻し／承認済みで絞り込めます。

- 初期状態にはオーナー名の取り違え、別発電所の写真の取り違えを含むチェック待ち2件と、承認済み4件があります。
- 「チェックする」→「AIチェックを実行」で記載内容と照合先の情報を比較します。名前は台帳に合わせて修正、写真は掲載写真の選択から差し替え、再チェックします。記載を変更しない場合は、確認の根拠を記録します。
- 最後に担当者名と全体確認を入力して承認します。理由を添えた差し戻しと再提出もでき、記録はブラウザに保存されます。
- 作成した報告書の操作欄から「報告書チェックに提出」を選ぶと、その時点の報告書を同じ点検案件のチェック対象に追加します。確認画面で修正した宛名・文章・写真は元の報告書にも反映されます。
- 点検予定・点検準備・報告書で、チェック待ち／差し戻し／承認済みと確認記録を共有します。差し戻し後は元の報告書を修正して再提出できます。同じ案件の提出を繰り返しても一覧に重複しません。
- 承認した内容と現在の報告書が一致するときだけ点検を完了できます。完了時には従来どおり修繕案件と1年後の点検予定を作成します。提出中・承認済みの作成画面は編集を止め、承認後の書き換えによる食い違いを防ぎます。

チェック応答は `src/services/reportCheckService.ts` のモックです。台帳・写真の登録情報・記入漏れの照合を再現し、画像認識や外部AIへの送信は行いません。

## モックの範囲

外部システムとの連携はありません。

- **発電所・点検履歴・修繕案件**：`src/mock/seed.ts` の架空のデータです。実行日を基準に作り直されます。
- **統合監視の出力・アラーム**：`src/mock/monitoring.ts`。時刻から作る晴天時の発電カーブと、固定のアラームです。監視システムからは取得していません。
- **現場入力の「残りを一括入力」**：`src/mock/scenario.ts` の値です。パネル割れの写真は図で代用しています。
- **データの保存先**：管理側の状態はこの端末のブラウザ（localStorage）です。現場との共有と写真は Netlify Blobs です。
- **判定基準**：JPEA「太陽光発電システム保守点検ガイドライン【10kW以上の一般用電気工作物】」表4・表2注をもとに `src/config/thresholds.ts` に定義しています。

## 本番化に必要なこと

- **認証・権限**：今は共有URL（推測されにくいトークン）を知っていれば誰でも閲覧・入力できます。担当者のログイン、案件単位のアクセス制御、共有URLの有効期限と失効が必要です。
- **実データ連携**：発電所台帳・顧客情報・過去の点検記録の取り込みと、各社の遠隔監視システム（アラームメール・API）との連携が必要です。報告書は、今お使いのフォーマットとの差を詰める必要があります。
- **データの保存**：管理側の状態はブラウザ内なので、複数の端末・担当者で共有できません。サーバー側のデータベースとバックアップが必要です。
- **写真の保存期間**：写真は Netlify Blobs に期限なしで保存されます。保存期間・削除の方針・容量の上限、写真に写り込む個人情報の扱いを決める必要があります。
- **現場の通信**：電波の弱い現場では、入力を端末に溜めて後で送る（オフライン対応）必要があります。

## 構成

- `src/screens/`：画面（統合監視、点検予定、点検準備・結果確認、写真確認、報告書、修繕案件、発電所カルテ、現場画面 `field/`）
- `src/logic/`：判定・確認ポイント・提案文・報告書・修繕の純粋関数（単体テストあり）
- `src/config/`：判定基準、目視項目、報告書の発行者
- `src/services/`：localStorageへの保存、現場との共有（`netlify/functions/inspection.ts` を呼ぶ）
- `DESIGN.md`：デザインシステム（色・文字・部品・表記）
- `AGENTS.md`：開発のルール
